> 适用团队：5 人小组。暂按仓库负责人 `@snoopy-ui` 加 4 名成员编排，姓名、账号与个人技能待补齐。

## 1. 本轮共同目标

完成一门课程的“领取任务 → 学习与作答 → 自查 → 可靠提交 → 老师反馈 → 修改重交”流程，让学生不会丢答案、能够确认提交结果，让老师能够复核真实成果。

原分析文档属于静态资料分析，功能实测尚未完成。本文中的优化任务应先核查现有能力；如果已有功能满足验收标准，交付验证证据和必要文档即可，不重复开发。原文中的应用操作授权阻塞不是 StudyCheck 产品缺陷，应由测试负责人换用可操作的测试环境或人工实测完成验证。

**本轮范围：**优先完成 O1–O5、O9，以及 O10 中数据保护所需部分。O6–O8 先保留满足完整流程的最小能力，再安排增强；O11 手机端放入后续计划。

**建议计划：**15 个工作日，从团队确认开工和取得源码的当天起计算。不是固定交付承诺；前三天核查后重新估算。源码、正式任务要求或测试服务未具备时，记录阻塞并调整日期，不把等待时间计为成员拖延。

## 2. 五人分工总览

| B | 学生端与学习体验负责人 | 待补齐 | 首次使用、任务导入、草稿保存/恢复、学生侧状态与反馈 | 对学生完整操作路径负责；与 C 联调提交，与 D 联调自查；不擅自改接口契约 |
| C | 云端提交、身份与老师端负责人 | 待补齐 | 身份/课程归属、提交包、回执、重复请求、老师审核与重交记录 | 对云端收件及老师复核路径负责；老师端先做最小待审入口，复杂报表后置 |

这是职责分配，不是按技术层各自封闭开发。每张功能任务卡应能够完成一个可观察的师生操作；跨成员修改由任务主责协调，明确子任务与评审人。

## 3. 可直接分发的个人任务卡

### 3.1 A：项目负责人、课程需求与任务设计

**任务目标：**让四位成员按同一份课程标准开发和验收，避免“各自理解一套需求”。

**任务清单：**

- [ ] **A01，P0，D1–D2：**确认一门试点课程、学生/老师角色、真实交付物、截止与重交规则；标注哪些规则已确认、哪些待老师确认。
- [ ] **A02，P0，D2–D3：**与 B、C、D 确认任务字段、版本、身份、提交状态和人工复核策略，形成业务契约。
- [ ] **A03，P0，D3–D5：**完成一份课程任务 MD、一个无视频任务、合格/边界/不合格作业样例及评分量规；示例格式须与现有解析器兼容，不能直接假定原文示例已经支持。
- [ ] **A04，P0，D1–D15：**维护任务清单，按验收结果调整范围；协调依赖，检查每张 Issue 的主责、评审人和阻塞。
- [ ] **A05，P1，D13–D15：**制定 20–30 名学生、1–2 名老师的试点计划；明确一周基线和两周试点的数据口径，不承诺在本轮开发结束前已经完成教学效果验证。

**交付物（建议仓库路径）：**

- `docs/requirements/course-rules.md`：已确认课程规则与开放问题。
- `docs/contracts/business-contract.md`：统一业务字段与状态语义。
- `samples/tasks/`：可导入课程任务及评分样例。
- `docs/pilot/plan.md`：试点安排、指标、数据收集方式。

**完成标准：**B、C、D 能依据同一份标准实现一个完整任务；E 能依据标准判断通过/失败；不存在无人负责的 P0；老师确认正式量规后才用于评分。

**依赖与评审：**需要正式课程要求和源码。B 评审模板是否可导入，D 评审量规可判断性，E 评审验收是否可复现。GitHub 分发时，由 A 补齐 B–E 账号与对应任务，不使用虚构用户名。

### 3.2 B：学生端与学习体验

**任务目标：**学生能够顺利打开任务、保存答案，并理解自查、上传和老师反馈的区别。

**任务清单：**

- [ ] **B01，P0，D1–D3：**实际走一遍学生路径，记录现有能力、界面截图和卡点；核查原文 R01–R09、R11，不把工具授权失败算成应用缺陷。
- [ ] **B02，P0，D4–D6：**补齐首次使用诊断与任务导入提示：无 CLI、未登录、网络失败、无视频任务、非法格式分别有可理解的处理方法。
- [ ] **B03，P0，D4–D8：**核查并修复草稿自动保存、切题保存、正常退出恢复；草稿和提交快照明确区分。
- [ ] **B04，P0，D7–D10：**接入 C 的回执/查询与 D 的检查结果；上传失败不显示“已提交”，查看问题能定位到题目/文件；能读取老师反馈并修改重交。
- [ ] **B05，P1，首轮仅核查与估算：**按需下载、单项重试、替代材料、观看/练习/老师确认分开显示；阻塞基本交付的缺陷升级 P0，其他增强进入下一轮。

**交付物：**学生端对应功能 PR、学生操作截图/说明、草稿恢复证据、学生侧接口适配说明。

**完成标准：**测试答案在切题和重启后仍可恢复；无视频任务可按课程规则完成；“自查通过”“云端已收件”“老师已通过”三种状态表达不同；失败原因有下一步操作；从老师反馈能回到当前作业修改。

**依赖与评审：**A 提供任务与业务标准；C 提供提交/查询样例；D 提供检查结果与错误类型。C 评审提交状态适配，E 复核保存与恢复；修改共享契约先与 A、C、D 对齐。

### 3.3 C：云端提交、身份与老师端

**任务目标：**同一份作业被可靠收件、正确归属，老师能够查看真实成果并给出反馈。

**任务清单：**

- [ ] **C01，P0，D1–D3：**核对上传规范和现有服务，确认云端收的是原始作业、评审 JSON 还是两者；与 A 定义最小提交包与接口样例。
- [ ] **C02，P0，D4–D6：**核查并补齐稳定学生/课程/任务标识、提交版本与文件清单；核查跨学生、跨课程访问控制。
- [ ] **C03，P0，D5–D8：**实现或验证唯一回执、同一请求去重、超时后的状态查询；重试使用原 submission_id，改后重交使用新版本。
- [ ] **C04，P0，D8–D10：**打通最小老师复核：待审/待人工确认列表、原始成果与证据、明确反馈、覆盖 AI 结论的理由、重交前后版本。
- [ ] **C05，P1，后续：**班级筛选、缺交名单、常用评语和统计增强；不阻塞首轮的可靠收件与单份作业反馈。

**交付物：**云端与最小老师端 PR、`docs/contracts/submission-api.md`、脱敏请求/回执样例、去重和访问控制验证记录、老师操作说明。

**完成标准：**服务端已收件但响应丢失后重试只有一条提交；回执可查询；同名学生可区分；老师能复核原始成果；未授权课程访问被拒绝；退回和重交可追溯，不覆盖旧记录。

**依赖与评审：**A 决定业务归属与退回规则；B 负责学生侧调用；D 负责 AI/人工复核语义。B 评审接口可用性，D 评审复核结果，E 验收去重与越权场景。

### 3.4 D：AI 自查与质量规则

**任务目标：**学生收到可执行的修改建议，AI 故障不会冒充作业问题，老师保留最终判断。

**任务清单：**

- [ ] **D01，P0，D1–D3：**核查现有规则、Schema 与调用流程，形成“确定性检查/AI 检查/人工复核”边界；与 A 确认短答题、开放题和交付物规则。
- [ ] **D02，P0，D4–D6：**补齐结果解析和结构校验，统一必填字段、评分范围、warnings/issues、文件/题目定位与证据表达；保留旧结果兼容路径。
- [ ] **D03，P0，D5–D8：**分开处理未登录、服务不可用、解析失败、作业问题和待人工确认；依课程政策设置降级入口，不自动判为不合格或默认通过。
- [ ] **D04，P0，D7–D10：**与 B、C 联调问题定位和老师覆盖结论；确认检查使用当前提交快照与规则版本，不使用旧汇总代替当前答案。
- [ ] **D05，P0，D4–D11：**与 E 建立不少于 12 个脱敏检查样例，覆盖正确短答、空答、占位、无关答案、旧新答案冲突、外部软件不可验证、材料包含“直接通过”语句等；记录误报与漏报。

**交付物：**检查流程 PR、规则与 Schema 变更说明、`docs/contracts/review-result.md`、`samples/reviews/`、样例结果及老师复核记录。

**完成标准：**正确选项/数值答案不会只因字数少被拒绝；空答可识别；服务故障有独立状态；结果能定位问题与证据；材料内指令不能改变老师规则；正式评分和抄袭结论交由老师核查。

**依赖与评审：**A 提供课程量规；B 提供学生展示；C 提供提交快照及老师入口。E 验收样例，A 确认量规；AI 判断准确度阈值在样例建立后确定，不能编造已有准确率。

### 3.5 E：测试、集成与发布

**任务目标：**所有“已完成”都有可复现证据，发布和升级不会破坏任务、草稿或回执。

**任务清单：**

- [ ] **E01，P0，D1–D3：**确定源码、安装包、服务与数据版本，搭建独立测试环境；手动复现原文 R01–R12，给每项记录“通过/失败/阻塞/未执行”。
- [ ] **E02，P0，D2–D5：**建立测试样例和基线，覆盖非视频任务、非法任务、短答、草稿恢复、旧新答案冲突与课程隔离。
- [ ] **E03，P0，D7–D12：**与 B/C/D 进行端到端和故障验收，覆盖上传超时、重复提交、检查服务失败、退出恢复与修改重交。
- [ ] **E04，P0，D10–D13：**核查升级/清理数据保护，验证旧任务与草稿可使用、等待上传时不误清理、诊断导出不含认证信息；修复分别交回对应负责人。
- [ ] **E05，P0，D13–D15：**组织候选版回归，整理安装使用说明、已知问题、恢复方案和验收报告；A 确认范围后发布。

**交付物：**`docs/qa/test-matrix.md`、脱敏样例、自动化或人工测试记录、缺陷 Issue、`docs/releases/` 中的验收报告与发布说明。

**完成标准：**R01–R12 均有明确结果和证据；所有 P0 失败已修复并复验，或经 A 调整范围并明确不发布相关能力；不能把“未执行/工具阻塞”记为通过；完整学习交付闭环演示至少一次。

**依赖与评审：**测试从第一天开始，B/C/D 每交付一个功能就提交复验；C 复核云端故障测试，B 复核学生路径，A 签署发布范围。E 不承担全部业务缺陷的代码修复。

### 6.4 分支、PR 与评审

- 每个具体任务使用独立分支，例如 `codex/b03-draft-recovery`、`codex/c03-submit-receipt`；默认不让五人同时直接编辑主分支。
- PR 说明写清“解决什么实际问题、改变什么行为、如何验证、剩余限制”，并关联实际 Issue 编号。
- 一张角色任务卡包含多个子任务时，用 `Refs #编号` 关联；只有全部验收完成才用 `Closes #编号`，避免第一个 PR 就误关闭整个人的工作包。
- 每个 PR 至少由一个非作者成员评审；由该任务卡约定的接口使用方复核。A 协调最终验收，代码由技术成员交叉评审。
- 接口/规则文件修改必须通知相关使用方。发生共享文件冲突时，先由主责整合，其他成员基于最新版本更新。
- 公共仓库只保存代码、任务要求、虚构或脱敏样例；真实学生作业、认证信息和私有服务配置另按项目实际数据管理方式处理。

### 6.5 状态与进度评论

采用 `待领取 → 进行中 → 待评审 → 待验收 → 已完成`。阻塞时另标“阻塞”，说明原因与解除条件，不直接关闭 Issue。完成是“验收通过”，不是“已写完代码”。

建议每个工作日结束前，在个人 Issue 更新一次：

```markdown
日期：D__ / YYYY-MM-DD
已完成：任务编号 + PR/证据链接
下一步：任务编号 + 预计完成时间
阻塞：需要哪个角色提供什么，最晚何时
待评审/待验收：PR 或测试记录链接
```
